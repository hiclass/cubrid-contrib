cub_top (C) — CUBRID 메모리 관측 (단일 파일 C99, 외부 의존 0)

사용: cub_top [옵션]
  [db명]            볼 데이터베이스 (생략 시 알파벳순 첫 번째, 라이브에서 < > 로 이동)
  (없음)           드릴다운 트리 (기본, 1회 출력)
  -t                 terse key=value (모니터링 연동·백데이터)
  --json             -t 와 같은 내용을 JSON 오브젝트로 (키·값·순서 동일, -t 자동 포함)
  -b, --live         btop 대시보드 (라이브)
  --heap             방법 A(힙 히스토그램) 포함
  --ascii            라벨을 영문으로 강제 (자동: 비 UTF-8 로케일·한글 폭 미지원 tty 는 영문)
  --ko               한글 라벨 강제 (자동 판정이 영문으로 잘못 내렸을 때)
  --offsets F        오프셋 표 파일/디렉터리 (tools/collect-offsets.sh 산출물 — 디렉터리면 버전 자동 선택; 생략 시 실행파일 옆 offsets/ 자동 탐색)
  --hot              최근접근(hot) 측정 켜기 — clear_refs 쓰기 필요(기본 OFF: 대상 PTE 전수 순회 ~30ms/GB + minor fault 유발)
  --hot-limit-gb N   핫 측정 자동 해제 임계 상주 크기(기본 2GB) — 이보다 크면 --hot 이어도 끈다
  --hot-every S      핫 측정 최소 간격(초, 기본 60) — 매 프레임 호출하지 않는다
  --no-hot           (하위호환) 핫 측정 끄기 — 기본이 이미 OFF 다
  --bcb-dump F       버퍼풀 BCB 스냅샷을 파일 F 로 (cub_volmap --bufmap F 가 지도에 얹음; 라이브는 매 프레임 갱신)
  --capacity-state F 용량 상한(포화 시 관측 IOPS) 기억 파일 — 재실행해도 헤드룸%를 이어서 판정
  -p, --plot         시계열 플롯 (라이브, p 키로 대시보드와 상호 전환)
  --interval S       샘플 창(초, 기본 0.5)
  --record F         라이브 프레임을 파일 F 로 기록 (JSONL — -t/--json 과 같은 키)
  --replay F         기록 파일 F 를 재생 (서버·/proc 불필요, -b/-p 키 그대로)
  --replay-speed N   재생 배속 (1=실측 간격, 0=최대속도, 기본 1)
  --dump-hist        히스토리 1샘플을 stderr 로 덤프 (수치 대조·진단용)
  -h, --help, /h     이 도움말


── 환경변수 CUBRID ──
  CUBRID=<설치경로>  설정 시 시작할 때 한 번 '<경로>/bin/cubrid paramdump <db>' 를 실행해
  서버가 실제로 적용 중인 파라미터를 읽는다(셸을 거치지 않고 execvp, 최대 5초).
  없으면 <경로>/conf/cubrid.conf 를 직접 파싱하고, 그것도 없으면 아래가 모두 빠진다:
    · data_buffer/log_buffer 의 '설정 대비 %' 판정 — 설정값이 없어 초과 여부를 알 수 없다
    · 파라미터 귀속률 — 설정으로 설명되는 몫을 셀 수 없어 표시되지 않는다
    · DB 페이지 크기 — data_buffer_size/pages 로 역산한다(실패 시 16KB 로 가정)
    · 방법 B 자기검증 — num_buffers 와 data_buffer_pages 대조가 불가해 힙 B 가 꺼진다
    · 렌즈2(설정초과)·하단 '메모리 파라미터' 표 전체
  즉 RSS/PSS 같은 실측은 그대로 나오지만, '왜 이만큼인가' 를 설명하는 축이 사라진다.

── 여러 데이터베이스(인스턴스) ──
  cub_top <db명>     그 DB 를 본다.  생략하면 가동 중인 것 중 알파벳순 첫 번째
  라이브에서 < > 로 이동. 상세 추적은 화면에 보이는 DB 하나뿐이고,
  나머지는 총량만 집계한다(clear_refs 를 전부에 돌리면 대상 서버가 느려지기 때문).
  terse 는 instance.<db>.* 로 모든 인스턴스를 내보내며 tracked=1 이 현재 추적 대상이다.

── 두 가지 라이브 화면 ──
  대시보드(-b)  현재 상태 한 장. p 로 시계열과 오간다. 키는 라이브 h 도움말 첫 절 참조.
  시계열(-p)    같은 값의 시간 흐름(4패널 A~D). p 로 대시보드로 돌아온다.
  배치(-t · --json · 옵션 없이)  한 번 수집해 텍스트로 낸다 — 모니터링·보고서 연동용.

── 대시보드 화면 구성 (위에서 아래로) ──
  ① OS 컨텍스트(호스트 CPU·메모리·인스턴스) ② 프로세스(티어별 PSS·코어)
  ③ RSS · 서버(영역·값 4열) ④ 동적 메모리 상세(B/A) ⑤ 메모리 추이(+load) ⑥ I/O 순으로 쌓인다.
  아래 절 설명도 같은 순서다 — 화면에서 보이는 자리 그대로 찾아 내려가면 된다.

── ① OS 컨텍스트 — CPU 와 load ──
  CPU 32c/64t     물리 32 코어 / 논리 64 스레드. 다르면 하이퍼스레딩이다.
                  물리보다 많은 부하는 같은 코어를 나눠 쓰는 것이라 선형으로 안 빨라진다.
  total|used|pct  total=논리코어, used=사용 중 코어 수, pct=전체 사용률.
                  used 는 '몇 코어어치가 돌고 있나' 라 프로세스 박스의 코어 수와 바로 비교된다.
  막대(게이지)    코어를 바쁜 순으로 정렬해 왼쪽부터 그린 것 — 합계가 아니라 분포다.
                  색으로 구분한다 — 적색=포화(≥95%) 주황=높음(≥50%)
                  녹색=중간(≥10%) 회색=유휴. 글리프는 다른 게이지와 같다.
                  used 12 이 12코어에 고르게 퍼진 것인지 6개가 100%인지는 합계로는
                  구분되지 않는다 — 뒤엣것이 병목이고, 왼쪽 붉은 구간의 폭이 그것이다.
                  ※ 코어가 막대 폭보다 많으면 한 칸이 여러 코어를 대표하며 그 구간의
                    최댓값을 그린다(포화를 평균으로 감추지 않기 위함). 그래서 칸 수에
                    코어 수를 곱해 읽으면 안 된다 — 정확한 개수는 옆의 sat 숫자를 볼 것.
  sat N           포화 코어 수 — 사용률 95% 이상인 코어가 몇 개인가.
                  포화 직전(50~95%)은 막대의 주황 구간이 보여준다.
                  btop 의 코어별 미터에서 100% 칸을 세는 것과 같은 값이다.
                  이 값이 물리코어 수에 근접하면 CPU 가 병목이다. 반대로 used 는 큰데
                  sat 이 0 이면 부하가 고르게 퍼진 것이라 아직 여유가 있다.
  us  user        사용자 코드. 질의 처리·정렬·조인 등 엔진이 실제 일한 몫
  sy  system      커널. I/O 발행, 락, 컨텍스트 스위치. us 대비 과도하면 경합을 의심
  load 1/5/15     최근 1·5·15분 평균 실행대기 태스크 수. CPU 사용률이 아니다 —
                  리눅스에서는 D 상태(디스크 대기)도 포함하므로, CPU 가 한가해도
                  I/O 가 막히면 올라간다. 논리코어 수(64)를 넘으면 대기가 쌓이는 중.
                  전체 호스트 값이라 인스턴스별로 나눌 수 없어 박스 제목에 둔다.

── ② 프로세스 박스가 PSS 인 이유 · 티어별 CPU ──
  PSS = 공유 페이지를 쓰는 프로세스 수로 나눠 배분한 상주량.
  libcubrid.so 10M 을 5개가 공유하면 각자 2M 로 잡힌다 → 행을 다 더해도 이중 계상이
  없어 All 합계가 성립한다. RSS 로 재면 같은 페이지가 여러 번 세어져 합이 부풀려진다.
  프로세스 박스   각 티어(master/server/pl/broker/CAS) 앞의 숫자가 그 티어의 코어 수.
                  전부 더하면 OS 의 used 이하여야 정상이다(나머지는 CUBRID 밖 프로세스).
                  색으로 크기를 구분한다 — 회색 · =유휴, 청록 <1코어, 노랑 1코어 이상,
                  주황=눈에 띄는 부하, 적색=물리코어 수 초과. 0 은 숫자 대신 · 로 눌러
                  실제로 돌고 있는 티어만 눈에 들어오게 했다.
  ※ 다른 도구와 대조할 때
    · server 의 CPU 는 top 과 같은 '1코어=100%' 규약이라 100% 를 넘을 수 있다.
      OS 박스의 코어 수와 견주려면 100 으로 나눌 것(terse 는 tier.*_cores 로 이미 환산).
    · Memory 의 used 는 MemTotal-MemAvailable 로 top 과 같은 정의다.
      htop 은 Shmem 을 달리 처리해 수 GB 낮게 나오는데, 오차가 아니라 정의 차이다.

── ③ RSS · 서버 — 각 항목이 알려주는 것 ──
  data_buffer     페이지 버퍼. 설정보다 큰 게 정상(BCB·victim 배열이 같은 매핑에 포함)
  log_buffer      로그 버퍼. 선할당이라 설정≈상주
  dynamic-heap    정렬·캐시·세션이 섞인 동적 힙 → 아래 [B]/[A] 로 분해
  thread stacks   워커 스택. 예약 크고 상주 극소가 정상
  glibc arena     할당자 예약. 상주 0이면 물리 메모리 미사용
  (설정 X, 할당 Y%)  설정 대비 매핑 비율. >105% 면 초과
  핫 N% 상주 중 실제 접근 비율. 낮으면 올려두고 안 만지는 메모리
  Σ 합계          4열의 합. rss 합 = 프로세스 RSS(항등). 프로세스 박스의 PSS 와는
                  공유 .so 배분만큼 다르며(오류 아님), 그 값이 라벨에 함께 적힌다.

── 파라미터 귀속률 — 화면 표기 "설정으로 설명 N%" (영역 박스 제목 옆) ──
  서버 메모리 중 cubrid.conf 설정으로 '왜 이만큼인지' 설명되는 비율.
    귀속   data_buffer(data_buffer_size), log_buffer(log_buffer_size)
    비귀속 dynamic-heap, thread stacks, code(.so) 등 — 설정으로 통제되지 않는 부분
  읽는 법:
    높다(90%대)   정상. 메모리 대부분이 설정대로다
    떨어진다      dynamic-heap 이 자라고 있다는 뜻 — 아래 heap 박스로 내려가
                  무엇이 늘었는지 확인할 것([a] 로 방법 A 를 돌리면 더 쪼개진다)
  즉 이 값은 'heap 박스를 들여다볼 필요가 있는가' 를 알려주는 신호다.

── 관측 등급 (값 왼쪽 1글자) ──
  ● 측정    OS/엔진이 직접 보고. 신뢰 가능
  ◐ 예약    매핑만 확인 — 실사용과 크게 다를 수 있음
  ◌ 추정    크기 패턴 추정 — 상대 비중만
  ? 미귀속  아직 분해되지 않음 — 해석하지 말 것

── ④ 동적 메모리 상세(= glibc malloc 힙) — B=정확 · A=크기 추정 ──
  ※ 여기서 '힙'은 프로세스의 동적 할당 영역(malloc)이다. 테이블 데이터가 저장되는
     스토리지의 '힙 파일'(HFID)과는 다른 것이며, 그쪽은 cub_volmap 이 다룬다.
  [B] 항목        엔진이 직접 보고하는 값 → 정확. plan·결과·필터 캐시·락·세션·카탈로그·연결
  lock table (tran)  lk_Gl.tran_lock_table — 트랜잭션별 락 보유 슬롯이다.
                  num_trans x 152B 로, 접속 상한에 비례해 미리 잡힌다.
                  ※ cubrid lockdb 의 "Object Lock Table" 과는 다른 구조다.
                    저쪽은 잠긴 객체의 LK_ENTRY/LK_RES 풀(예: 1000개 242K)이고
                    이쪽은 트랜잭션 슬롯(예: 101개 15K)이라 값이 다른 것이 정상이다.
  [A] 항목        glibc 청크 분포 추정. 정렬·해시 작업버퍼 등 B가 못 잡는 것
  [A] overcount   A 합계가 상주 초과(free 청크·비상주 포함) — 정상, 상한으로 읽을 것

── ⓑ 실행 계정 — 서버를 띄운 계정으로 실행할 것 ──
  root 일 필요는 없다. 서버를 띄운 계정(보통 cubrid)이면 전 기능이 동작한다.
  그 계정이 아니면 커널 ptrace 검사로 mem/smaps/io 가 막혀 55개 키가 빠진다
  (영역별 분해·PSS·동적 메모리 상세 B·버퍼풀 BCB·로그 LSA·proc_iops·hot).
  남는 것: OS 전체·장치 I/O·cubrid.conf·서버 총량(status 폴백으로 VmRSS 는 살린다).
  못 본 값은 0 으로 내지 않고 perm.limited=1 과 사유를 함께 표기한다 — 0 으로 내면
  모니터링이 '메모리를 안 쓴다' 로 오독한다. 자세한 대조표는 docs/limitations.md §15.

── ⓐ 용량(capacity) — 증설·축소·개선을 무엇으로 판단하나 ──
  숲 관점의 축이다: 수요(지금 얼마 쓰나) · 상한(이 환경이 얼마까지 되나) · 헤드룸(남은 여유).
  수요   dev IOPS = 장치 전체, this server IOPS = 이 인스턴스 귀속(/proc/<pid>/io).
  지연   await = 요청당 대기(ms). IOPS 는 낮은데 await 가 크면 'IOPS 증설'이 아니라
         '더 빠른 스토리지'가 답이다. queue = 평균 큐 깊이.
  상한   포화(사용률 90% 이상) 또는 큐가 쌓인 순간의 IOPS 를 그 환경의 실효 상한으로 기억한다.
         **하나의 숫자로 기억하지 않는다.** 같은 장치라도 4KB 랜덤과 128KB 순차는 IOPS 상한이
         자릿수로 다르므로, I/O 프로파일 = 평균 요청 크기(<8KB / 8-64KB / >64KB) x 읽기 비중
         (write-heavy <30% / mixed / read-heavy >70%) 9칸으로 나눠 칸마다 따로 기억하고,
         지금 프로파일과 **같은 칸**의 상한하고만 비교한다. 다른 칸 값을 빌려 쓰면
         (128KB 로 잰 상한을 4KB 워크로드에 적용) '여유 있다' 는 거짓 판정이 나온다.
         --capacity-state FILE 로 보존하면 재실행해도 칸별 상한을 이어서 판정한다.
         그 칸이 한 번도 포화하지 않았으면 '이 칸은 미관측'으로 표기한다(추정을 사실로 위장하지 않는다).
  버퍼   히트율의 출처가 두 가지다.
         perfmon   엔진 카운터가 **이미 돌고 있을 때**(statdump·csql ;histo 등 watcher 존재)
                   그 값을 읽는다. 우리가 watcher 를 만들지는 않는다(무침습 절대 조건).
         turnover  카운터가 정지면 BCB 스냅샷 두 장의 VPID 집합 차이로 회전율을 낸다.
                   적재 pg/s = 미스, 재적재% = 빠졌다 다시 들어온 비율(작업집합>버퍼 신호).
  판정   ⚠ 용량 한계 = 헤드룸 80%↑ **그리고** 장치가 실제로 밀릴 때(await 20ms↑ 또는 큐 10↑).
         헤드룸만 높고 적체가 없으면 '상한 근접 — 한계 단정 불가'로만 말하고 증설을 권고하지 않는다.
         상한은 과거 다른 순간의 관측치라 워크로드가 가벼워지기만 해도 80%를 넘길 수 있기 때문이다.
         · ⚠ 지연 병목(await 20ms↑ & IOPS 낮음)
         ⚠ 버퍼 부족(적재 많고 재적재 30%↑) · ⚠ 스캔(적재 많고 재적재 없음 — 증설 무효)
         · 과다 할당(버퍼 60% 미사용 & 적재 거의 없음 — 축소 가능) · · 여유
  비용   취합 예산 0.5초. 넘으면 그 프레임 값을 버리고 '취합 생략'을 화면에 남긴다.
         실측 0.2~0.9ms(예산의 0.2% 미만). 대상 프로세스 쓰기 0, 접속·락 0.

── ④′ 버퍼풀 상태 — 페이지 슬롯 = 버퍼 제어블록(BCB, Buffer Control Block) (◌) ──
  pgbuf_Pool.BCB_table 배열을 방법 B 와 같은 경로로 통째 읽어 어떤 페이지가 버퍼에
  올라와 있고(resident) 몇 장이 아직 볼륨에 안 내려갔는지(dirty) 센다. 래치 없는 스냅샷.
  게이지: 전경=상주율, 배경(청색)=dirty 비율.  zones: hot/warm/cold = LRU 3구역,
  void = 적재/축출 전이 중, free = 빈 BCB.  victim 은 cold 에서 뽑고 dirty 는 건너뛴다.
  log: append = 로그 꼬리, flushed(nxio) = 디스크에 내려간 경계 → 차이 = 아직 fsync 안 된 로그.
  두 가지 '뒤처짐' 을 구분한다 — 둘 다 로그 꼬리(append) 기준이지만 대상이 다르다:
    fsync 지연 = append − flushed(nxio)     로그 자체가 디스크에 안 내려간 거리.
                 커밋 응답이 직접 느려지므로 더 급한 신호다.
    flush 지연 = append − oldest dirty LSA  데이터 페이지의 볼륨 반영이 뒤처진 거리
                 = 장애 시 redo 해야 할 길이. 정상에서도 0 보다 크며 크기보다 추세를 본다.
                 dirty 개수와 다르다 — 개수가 적어도 오래된 한 장이 남으면 이 값은 크다.  자기검증: VPID 이상치 1% · 헤더 읽기실패 50% · **재검 후** 잔여 불일치 5%(50% 초과면 비활성, 그 사이는 검증분만 집계).
  --bcb-dump F : 스냅샷을 파일로 → cub_volmap --bufmap F 로 볼륨 지도 위에 버퍼 상주/dirty 를 얹는다.

── ⑤ 메모리 추이 박스의 load(OS) 겹침 ──
  분홍=서버 전체, 적색=동적 힙, 노랑=load(OS, 1분). load 는 단위가 달라
  자체 최대 기준으로 모양만 겹치고, 실제 값·범위는 우측 범례에 있다.
  읽는 법: 메모리가 늘 때 load 도 같이 오르면 부하 기인 —
           load 는 평탄한데 메모리만 계속 오르면 누수를 의심할 것.

── ⑥ I/O 박스 — iowait · D스레드 · 항목 · 판정문 ──
  wa  iowait      ※ 'CPU 가 I/O 를 기다리며 바빴다' 가 아니다.
                  CPU 가 놀고 있었고(idle) 동시에 그 CPU 에 디스크 대기 태스크가
                  있었던 시간의 비율 — 즉 idle 의 하위 분류다. 함정 둘:
                    · 코어 수로 나뉜다. 64코어에서 한 프로세스가 디스크를 완전히
                      포화시켜도 wa 는 1~2% 로밖에 안 보인다
                    · CPU 가 바쁘면 idle 이 없어 wa 도 0 이 된다 → I/O 병목이 가려진다
                  그래서 wa 단독으로 판단하지 말고 아래 조합으로 읽을 것:
                    wa 낮음 + dev util 높음  CPU 가 바빠 wa 가 가려진 상태. 병목 가능성 있음
                    wa 높음 + dev util 높음  디스크 병목이 확실 — data_buffer 부족을 의심
                    wa 높음 + dev util 낮음  디스크가 아닌 대기이거나 측정 구간이 짧다
                    majflt 증가             버퍼에 없어 디스크에서 읽은 것 — 증설의 직접 근거
                  dev util 과 majflt 는 코어 수에 희석되지 않는 물리량이라 더 믿을 만하다.
                  ※ I/O 박스가 이 조합을 대신 판정해 한 줄로 알려준다(아래 참조).
  D스레드 n/m     iowait 행 오른쪽. cub_server 스레드 m 개 중 n 개가 D 상태
                  (디스크 응답을 기다리는 중단 불가 대기)라는 뜻이다.
                  wa 와 달리 코어 수로 희석되지 않아, 대기가 있으면 반드시 잡힌다.
                  0 이 아니면 그 순간 실제로 디스크에 막혀 있다는 직접 증거다.
  cache absorb    요청 읽기 중 디스크로 안 내려간 비율. 0% 면 캐시가 무효
  dev util        장치 포화도 — I/O 가 많은지의 1차 판정. 100%면 포화
  blkio wait      이 서버가 디스크를 기다린 시간의 비율(delayacct_blkio_ticks).
                  전 스레드 합이라 한 코어(100%)를 넘을 수 있다 — CPU 사용률과
                  같은 규약이다. cub_server 는 워커가 I/O 를 하므로 반드시 스레드를
                  모두 더해야 한다(메인 스레드만 보면 늘 0 이다).
                  pidstat -d 의 iodelay 와 같은 출처이며, 그쪽은 기본이 메인 스레드
                  기준이라(-t 로 스레드별) 값이 다르게 보일 수 있다.
                  비동기 대기는 안 잡히므로 0 을 '문제 없음'으로 단정하지 말 것.

── I/O 판정문 (I/O 박스 맨 아래) ──
  wa·장치 사용률·인스턴스 신호 세 가지를 조합해 결론을 한 줄로 낸다. 조건이
  풀려도 지워지지 않고 시각과 함께 최근 2건까지 남는다(지난 것은 회색) —
  I/O 이상은 순간적이라 지워지면 '봤는데 없어졌다' 가 되기 때문이다.

  판정에 쓰는 세 조건
    (1) wa 높음    iowait >= 100/코어수 x 0.5 (%). 코어 수에 맞춰 자동 조정된다 —
                   64코어면 0.78%, 32코어면 1.6%, 4코어면 12.5% (하한 0.5%).
                   고정 3% 같은 기준은 코어가 많으면 도달하지 않아 병목을 놓친다.
    (2) 장치 바쁨  최다사용 장치의 사용률 >= 80%. 장치를 식별했을 때만 성립한다.
    (3) 내 신호    이 인스턴스가 실제로 I/O 중이라는 증거. 넷 중 하나면 성립:
                   majflt >= 1/s · D스레드 > 0 · blkio >= 1% · 이 서버 io >= 1MB/s
                   ※ 컨테이너(overlay)에서는 DB 파일의 백킹 장치를 diskstats 에서
                     못 찾아 (2)가 인스턴스 부하와 이어지지 않는다. 그래서 (3)에
                     이 서버의 실제 읽기/쓰기량을 반드시 포함한다.

  나올 수 있는 경우 — 세 조건의 8조합이 판정 5종으로 모인다
   (1)(2)(3)  판정
    O  O  O   ⚠ 디스크 병목 — 셋 다 성립. 가장 확실한 신호다.
              data_buffer 를 늘려 디스크 읽기를 줄이는 것이 1차 대응이다.
    X  O  O   ⚠ wa 가 가려짐 — 장치는 바쁜데 wa 가 낮다. CPU 가 바빠 idle 이
              없으면 wa 도 0 이 된다(wa 는 idle 의 하위 분류). 병목일 수 있다.
    O  X  O   · 비디스크 대기 — wa 는 있는데 장치는 한가. 네트워크·NFS 대기이거나
    O  X  X     측정 구간이 짧아 장치 통계가 아직 안 잡힌 경우다.
    X  O  X   · 다른 프로세스의 부하 — 장치는 바쁘지만 이 인스턴스는 조용하다.
    O  O  X     CUBRID 문제가 아니므로 같은 호스트의 다른 프로세스를 볼 것.
    X  X  O   (표시 없음) — 이 서버가 I/O 를 하지만 wa 도 장치도 한가하다.
    X  X  X   (표시 없음) — 유휴. 정상 상태다.

  읽는 순서
    1) ⚠(적색·주황)이면 그 줄만 읽어도 결론이 난다.
    2) ·(회색)이면 이 인스턴스의 문제가 아니거나 판단하기 이른 상태다.
    3) 아무것도 없으면 I/O 는 정상이다 — 느리다면 CPU(OS 박스)나 잠금을 볼 것.
